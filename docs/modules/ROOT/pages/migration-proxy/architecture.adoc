= Migration Proxy :: Architecture
:navtitle: Architecture

The proxy is assembled as its own Guice module set on top of `GuiceJamesServer` (a mailbox-less Twake
Mail MTA, modelled on the James SMTP-only app), to which two custom concerns are added: the IMAP
byte-proxy and the migrated-users routing.

----
            IMAP clients                       SMTP clients / old & new backends
                 |                                          |
        :143 / :993 (proxy)                         :25 public   :26 relay
                 |                                          |
        +--------v---------+                      +---------v----------+
        | ProxyImapProcessor|                     |  SMTP server stack |
        |  (auth -> relay)  |                      |  (CoreCmdHandler)  |
        +--------+---------+                       +---------+----------+
                 |                                            | spool
          BackendRelay                               mailetcontainer.xml
        (raw byte piping)                          (recipient routing)
            |        |                            /        |          \
         old IMAP  new IMAP                 RemoteDelivery  RemoteDelivery  RemoteDelivery
                                              -> new          -> old         -> external
----

== IMAP byte-proxy

* `ProxyImapProcessor` is a minimal `ImapProcessor` that only answers `CAPABILITY`, negotiates
`STARTTLS` (delegated to James' `ImapSession#startTLS`) and authenticates the client. TLS (plaintext /
STARTTLS / implicit SSL) is provided by reusing James' `IMAPServer`.

* Authentication has two mutually exclusive modes. By default `LOGIN` and `AUTHENTICATE PLAIN` (James'
`PlainSaslMechanism`) both capture the user and password, replayed as-is against the backend. With
Kerberos enabled both are disabled in favour of `AUTHENTICATE GSSAPI` (James' `GssapiSaslMechanism`):
the proxy then holds no password and opens the backend session by SASL PLAIN delegation from a
configured backend administrator (`ImapPlainImpersonationBackendDialog`). Either way the proxy verifies
nothing itself -- it has no user database.

* `BackendResolver` picks the backend: migrated user -> new, otherwise -> old (from the
`MigratedUsersRepository`).

* `BackendRelay` opens a client connection to the resolved backend, authenticates there on the user's
behalf (`ImapBackendDialog`: tagged `LOGIN`, or the delegation dialog under Kerberos), then pipes raw bytes both ways between the client and
the backend channels. The handover is done in two steps so the IMAP tagged `OK` is emitted at the
right time. Per-backend options: implicit TLS, ignoring backend certificates, and `forwardProxyInfo`
(forward the inbound HAProxy PROXY protocol information to the backend, error if required but absent).
Kerberos delegation requires implicit TLS with certificate and hostname validation for both backends;
the proxy refuses to start with plaintext or ignored certificates because the delegated administrator
password is sent with SASL PLAIN.

== SMTP submission proxy (optional)

Opt-in (`submission.enabled=true`): authenticated submission (`:587` STARTTLS / `:465` implicit TLS)
gets the same treatment as IMAP, so the proxy needs no user database -- hence no LDAP -- for SMTP
either. The mail itself still goes through the backend of the user, which relays it back to the proxy
`:26` as with direct submission, so recipient routing is unchanged.

* The listeners are James `SMTPServer` instances (TLS, STARTTLS, PROXY protocol, connection limits)
whose command set is pinned to `SubmissionProxyHandlersLoader`: `EHLO`/`HELO`, `STARTTLS`, `AUTH`,
`NOOP`, `RSET`, `QUIT`. The mail transaction commands are answered `530` -- the proxy never accepts
mail on these ports.

* `SubmissionAuthCmdHandler` runs `AUTH PLAIN` / `AUTH LOGIN` only to capture the credentials
(delegation refused). `SubmissionBackendHandover` resolves the backend, and `BackendRelay` replays
them with `SmtpBackendDialog` (greeting, `EHLO`, `AUTH PLAIN`) before piping raw bytes. A backend
`535` is a `535 5.7.8` for the client; anything else (unreachable, timeout, `454`, unexpected reply)
is a `454 4.7.0` temporary failure, and the client may retry `AUTH` on the same session.

* Commands the client pipelined behind a single round-trip `AUTH PLAIN` (RFC 4954) are relayed in
order: the `235` is written first, a forwarder placed in front of the SMTP core handler relays the
lines the framer still dispatches, and the framer's partially received line is handed to that
forwarder before the connection becomes a bare byte pipe.

* Relayed sessions are registered like IMAP ones, so migrating a user cuts its submission sessions
too. Metrics are reported under `migrationProxy.submission.<backend>.*`.

== SMTP routing MTA

* Two SMTP servers enforce the relay policy *by port*: `:25` is public (no relay — non-local
recipients are rejected at RCPT) and `:26` is exposed only to the old/new backends (relay allowed).

* Accepted mail is spooled and processed by `mailetcontainer.xml`, whose `transport` processor routes
*per recipient* through three dedicated `RemoteDelivery` mailets, selected by matchers:
+
** `RecipientIsMigrated` (custom matcher querying the migrated-users repository) -> *new* gateway,
** `HostIsLocal` -> *old* gateway,
** `SMTPIsAuthNetwork` -> *external* (real MX delivery).
+
`RemoteDelivery` is terminal for the recipients it matches; the others fall through to the next mailet.

== Migrated users

* `MigratedUsersRepository` is backed by PostgreSQL (`PostgresMigratedUsersDAO`, table
`migrated_users`). It drives both the IMAP user routing and the SMTP `RecipientIsMigrated` matcher.

* The `/migratedUsers` webadmin route exposes `PUT` / `DELETE` / `GET` / `HEAD` to manage the list.

== Backend adaptation and mirroring

The old and new backends are configured so that:

* *authenticated local submissions are relayed entirely to the proxy* (`:26`) — a backend never
delivers its own users' outgoing mail itself;
* *unauthenticated mail (coming from the proxy) is delivered locally*.

This guarantees mail is delivered on the backend that hosts the recipient: a user on old writing to a
user on new is delivered on new, and conversely. See the backend configuration in
xref:migration-proxy/configuration.adoc[].

== TLS provider

Both the listening side and the backend client side follow the `james.tcnative.enabled` system
property: BoringSSL via netty-tcnative when set, the JDK provider (nio) by default.
